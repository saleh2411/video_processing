Final Project · Video Processing 0512-4263 · Concept & Method Report
Final Project — פרויקט מסכם

From a Shaky Corridor to a Calm Fjord

A shaky video of a person walking goes in; a stabilized video of the same person walking on a completely different background — with a tracking rectangle following him — comes out. Four classical blocks do all the work: Stabilization → Background Subtraction → Matting → Tracking. No deep learning anywhere. Every block below is explained with the theory from the course lecture notes (Video_Processing.pdf) and the exact way it is used in our code.

0   The task and the pipeline

Project definition (Final_Project_2526.pdf, Introduction)

"This project is about stabilization, background subtraction, matting and tracking. We will give you a shaky video of a person walking. You will implement several algorithms throughout this project in which eventually, you will output a stabilized video of that person walking, with a different background and rectangle around the person tracking it through the entire video."

INPUT.avi ──▶ [Stabilization] ──stabilize.avi──▶ [Background Subtraction] ──extracted.avi + binary.avi──▶ [Matting] ──matted.avi + alpha.avi──▶ [Tracking] ──▶ OUTPUT.avi ▲ background.jpg
What each block must deliver (project PDF, "Main steps")
  1. Stabilization — remove the hand-held camera shake from INPUT.avi → stabilize_ID1_ID2.avi. Black pixels near the frame edges after warping are explicitly allowed (FAQ #1), and blurring must be avoided because it damages the matting stage later.
  2. Background subtraction — extract the walking person → extracted_ID1_ID2.avi (person keeps his original colors, 0 everywhere else — FAQ #2) and binary_ID1_ID2.avi (1 = person, 0 = not person — FAQ #3).
  3. Matting — place the person inside background.jpg → matted_ID1_ID2.avi, plus alpha_ID1_ID2.avi holding per-pixel opacity in [0,1] (FAQ #4), scaled to [0,255] uint8 for saving (FAQ #5). Inputs to this block are the background image, stabilize.avi and binary.avi (FAQ #7).
  4. Tracking — automatically select the person in the matted video and follow it with a rectangle in all frames → OUTPUT_ID1_ID2.avi + tracking.json mapping each frame number to [ROW, COL, HEIGHT, WIDTH].

All videos are processed and written as color videos (the project PDF requires color inputs and outputs at every step; only binary.avi is exempt — we still save it as 3-channel for safety). A timing.json records, in seconds from the start of main.py, when each output video finished being filled with all its frames. Everything runs from a single command, python Code/main.py, with relative paths only, no user input and no windows.

1   Stabilization

Lecture — motion representation (Video_Processing.pdf, pages 4–6)

The Affine transformation is a linear transformation with translation:

$$ \begin{pmatrix} x' \\ y' \end{pmatrix} = (A~~t)_{[2\times 3]} \begin{pmatrix} x \\ y \\ 1 \end{pmatrix} $$

Homography is a transformation of the form:

$$ \begin{pmatrix} x' \\ y' \\ 1 \end{pmatrix} \cong H \begin{pmatrix} x \\ y \\ 1 \end{pmatrix} $$

"When solving a tracking problem, the more parameters the model has, the harder it becomes to estimate them reliably, since noise can significantly affect the solution. If the object is small and far away, a linear transformation may be sufficient. If it is closer, an affine transformation might be more appropriate, and if the object is large and close to the camera, a homography may be required."

Lecture — optical flow & interest points (Video_Processing.pdf, pages 8–15)

The brightness-constancy linearization behind Lucas–Kanade:

$$ I_2(x,y) \approx I_1(x,y) + u\, I_x(x,y) + v\, I_y(x,y) $$

The goal of LK is to minimize:

$$ P^* = \arg\min_P \sum_X \big[I_2(W(X; P)) - I_1(X)\big]^2 $$

"Points of interest are usually corners of objects, where there are strong intensity changes in both the x and y directions… If the rank [of $B^TB$] is 1, the point lies on an edge. If the rank is 2, the point corresponds to a corner. Harris used this idea in his work. After detecting interest points, he applied the Lucas–Kanade method on a small window around each point to track it in the next frame."

"There are applications where LK alone is sufficient, such as video stabilization or tracking large objects… the process typically begins with HPD [Harris Point Detection] in the first frame to identify interest points. A small window is placed around each point, and LK is then used to track them in subsequent frames."

Lecture — RANSAC (Video_Processing.pdf, pages 24–25)

"When calculating transformations, there is a risk of matching false pairs of points. The RANSAC algorithm is designed to address this problem… The main problem here is the presence of outliers — false points that are incorrectly identified by the algorithm and negatively affect the solution… RANSAC addresses this by randomly selecting points many times and identifying the model that is consistent with the largest number of points. A point is considered consistent if, after applying the transformation… the distance between the transformed point and its corresponding point… is below a given threshold."

What our code does — Code/stabilization.py

The camera in INPUT.avi is hand-held and shaky, but the scene is static. So instead of merely smoothing the camera path, we lock every frame onto the coordinate system of the first frame — after stabilization the background becomes essentially still, which is exactly what the background subtraction stage needs.

  1. Corners — cv2.goodFeaturesToTrack detects up to 600 Shi–Tomasi corners in the previous frame (the min-eigenvalue variant of the Harris detector from the lecture: both eigenvalues of $B^TB$ must be large — a "rank 2" point).
  2. Optical flow — cv2.calcOpticalFlowPyrLK tracks the corners into the current frame with pyramidal Lucas–Kanade (4 pyramid levels, 21×21 windows). The pyramid handles shake displacements far larger than the few pixels the Taylor linearization can absorb at full resolution.
  3. Global motion model — from the tracked pairs, cv2.findHomography(…, cv2.RANSAC, 3.0) estimates the frame-to-frame homography. The scene (doors, posters, floor tiles) is large and close to the camera, so per the lecture's model-selection rule a homography — 8 parameters, exact for a rotating/shaking camera viewing a scene — is the right model. The corners that fall on the walking person do not obey the global background motion; RANSAC rejects them automatically as outliers, since the static background contributes the overwhelming majority of the corners.
  4. Composition — homographies compose: if $H_t$ maps frame $t$ onto frame $t-1$, then $H^{cum}_t = H_1 H_2 \cdots H_t$ maps frame $t$ all the way onto frame 0, and cv2.warpPerspective renders the stabilized frame.
  5. Drift correction — composing ~200 estimated homographies accumulates tiny errors. After warping we therefore run one more corner + LK + RANSAC pass between the reference frame and the warped frame, and fold the small residual homography back in. This keeps the background pixel-locked across the whole clip.

Why no smoothing / no blur

Warping with bilinear interpolation is the only resampling applied. No temporal smoothing of frames, no spatial blur — the project PDF warns that damaging image quality at this stage "can cause you problems in the matting stage". The black border pixels created by the warp are expected and allowed (FAQ #1).

Key idea RANSAC does two jobs at once here: it estimates the camera motion and it segments out the walking person (as outliers) without us ever telling it a person exists.

2   Background Subtraction

Lecture — background subtraction (Video_Processing.pdf, pages 52–56)

"Given a video, we will work on each pixel separately. We will observe its intensity profile over time… Therefore, the solution propose to do clustering… Note that the clusters are typically Gaussian-shaped rather than rectangular due to sensor noise." The per-pixel Gaussian mixture is

$$ f_x(x|\Phi) = \sum_{k=1}^K p(k)\, f_{x|k}(x|k, \theta_k), \qquad \theta_k = (\mu_k, \sigma_k) $$

and a new measurement is assigned to a component by the match test

$$ M_{k,t} = \begin{cases} 1 & \dfrac{x_t - \mu_{k,t-1}}{\sigma_{k,t-1}} < 2.5 \\[4pt] 0 & \text{O.W.} \end{cases} $$

"This is done by first sorting the Gaussians in descending order of $\frac{\omega_k}{\sigma_k}$. Here, $\omega_k$ represents how frequently the $k$-th Gaussian has been observed in the past — the higher its value, the more likely it belongs to the background. $\sigma_k$ represents the width of the Gaussian; smaller values indicate less variation in intensity, suggesting a static object."

What our code does — Code/background_subtraction.py

The lecture's GMM machinery exists because, in general, a pixel oscillates between several background modes (sky / leaves / sidewalk) and the model must be learned online. Our situation after stabilization is much friendlier: the background is static, we have the whole video offline, and each pixel shows its true background color most of the time — the person covers any given pixel only briefly while walking through. So the mixture collapses to one dominant Gaussian per pixel (the lecture's highest-$\omega_k/\sigma_k$ component), and we can estimate it in one shot with robust statistics instead of online EM updates:

$$ \mu(x) = \operatorname{median}_t\, I_t(x), \qquad \sigma(x) = \max\big(1.4826 \cdot \operatorname{MAD}_t(x),\ \sigma_{\min}\big) $$

The median and the MAD (median absolute deviation) ignore the minority of frames in which the person passes through the pixel — they play exactly the role of the mean and std of the dominant background Gaussian, but cannot be contaminated by the foreground. The factor 1.4826 converts MAD to a Gaussian-consistent std.

The decision rule = the lecture's match test

Working in CIE-Lab (L = illumination, a/b = chroma), each pixel of each frame gets a joint z-score

$$ z_c(x) = \frac{|I_t^c(x) - \mu^c(x)|}{\sigma^c(x)}, \qquad \text{score}(x) = \sqrt{\tfrac{1}{4} z_L^2 + z_a^2 + z_b^2} \;\gtrless\; T = 4.5 $$

— the same "how many sigmas away from the background Gaussian" test as the lecture's $2.5\sigma$ match, applied jointly over three channels. The L channel is down-weighted because cast shadows live almost entirely in L.

Cast-shadow suppression

The person casts a strong shadow on the wall and doors behind him. A shadow darkens the background without changing its chroma, so any foreground-flagged pixel with $0.35 < L/L_{bg} < 0.95$ and $|a-a_{bg}|, |b-b_{bg}| < 8$ is re-labeled background. This is the same rule OpenCV's MOG2 uses for its shadow output, expressed in Lab.

From pixels to a person

Morphological opening removes isolated specks, closing glues body parts, the largest connected component is kept (the project guarantees exactly one walking person — FAQ #6), and interior holes are filled by flood-fill. The result per frame: binary (person = 1) and extracted = frame × mask, so the person keeps exactly his original colors on a black background, as FAQ #2 requires.

Why not just run MOG2/KNN? FAQ #10 allows OpenCV's createBackgroundSubtractorMOG2/KNN, but they are online algorithms designed for streaming surveillance — they need warm-up frames, adapt while the person stands still, and would have to be explained in depth anyway. The offline median/MAD model is the same per-pixel Gaussian idea, deterministic, contamination-proof, and computed from ~60 sampled frames in seconds.

3   Matting

Lecture — video matting framework (Video_Processing.pdf, page 67)

"The purpose of video matting is taking the foreground of an image and insert it to a new background. The entire framework of video matting compromises: Input — a 3-channel image and scribbles of the foreground and the background. Trimap — a map of only 3 values: 1 — we confidently know the pixel is foreground. 0 — we confidently know the pixel is background. Undecided value $\phi$ — we are not sure. Opacity map — it will fill the undecided region with values which are between 0 and 1. Matting — takes an opacity map and a new background and performs the final matting."

Lecture — KDE, Bayes and distance maps (Video_Processing.pdf, pages 68–70)

"We will, therefore, work with what is called Kernel Density Estimation (KDE)… Instead [of a histogram], we would draw around each pixel a 'bell':"

$$ f(c|F) \propto \sum_{x \in \Omega_F} K(c, c(x)), \qquad K(c, c') \propto e^{-\frac{\|c - c'\|_2^2}{2\sigma^2}} $$

With uniform priors $P(F)=P(B)=\tfrac12$, Bayes gives:

$$ P(F|c) = \frac{f(c|F)}{f(c|F) + f(c|B)} $$

Then distance maps $D_F(x), D_B(x)$ to the foreground/background regions are computed, the image is split into $V_F$ and $V_B$, and a narrow band $B_\rho(\Delta)$ of radius $\rho$ is drawn around the boundary $\Delta$: inside $V_F$ and outside the band $\alpha_T = 1$; inside $V_B$ and outside the band $\alpha_T = 0$; inside the band $\alpha_T = \phi$.

Lecture — opacity map & matting (Video_Processing.pdf, pages 71–73)

"Now, our focus is on a specific region with much more limited color variation. We have a lot more samples of the foreground and background on the boundary. Thus, we will estimate again the distribution functions for refinement…"

$$ \forall x \in B_\rho(\Delta): \quad \alpha(x) = \frac{w_F(x)}{w_F(x) + w_B(x)}, \qquad w_F(x) = \tilde{D}_F(x)^{-r}\, \tilde{P}_F(x), \quad r \in (0, 2] $$

For the final composite the direct blend is $J(x) = \alpha(x)\, c(x) + (1 - \alpha(x))\, B(x)$; the lecture refines it at the boundary by recovering a pure foreground color from confident neighbours, to avoid mixing the old background's color into the new one.

What our code does — Code/matting.py

The binary mask replaces the scribbles

The lecture bootstraps from user scribbles because it assumes nothing else is known. We are in a better position: the background-subtraction stage already produced a reliable binary mask per frame. Eroding the mask by $\rho = 10$ px gives confident foreground ($\alpha=1$), dilating it by $\rho$ gives the outer edge of the unknown band; everything further out is confident background ($\alpha=0$). That erode/dilate band around the person's contour is the lecture's trimap with band radius $\rho$ (the lecture recommends $\rho \approx$ 5–15 px).

Local KDE, computed the fast way

Following the trimap-refinement idea ("we have a lot more samples of the foreground and background on the boundary"), the color models are estimated only from pixels within 25 px of the band — locally, per frame. The KDE itself is computed as a 256-bin histogram per Lab channel smoothed with a Gaussian kernel and used as a lookup table: placing a Gaussian bell on every sample and summing is mathematically identical to blurring the sample histogram with that bell. This is the practical answer to the lecture's complexity concern (pages 73–74: naive KDE is $O(|\Omega|\cdot|\Omega'|)$, fixed there by low-rank kernel factorization): our LUT costs $O(|\Omega'| + 256)$ per channel, and evaluating a pixel is one table lookup. Channels are combined as independent likelihoods (naive Bayes), and uniform priors give $P(F|c)$ exactly as in the lecture.

Opacity map

For every band pixel we compute distance transforms $D_F$ (to confident foreground) and $D_B$ (to confident background) — a Euclidean approximation of the lecture's geodesic distances, accurate here because the band is only ~20 px wide — and blend color evidence with spatial evidence using the lecture's own formula with $r = 2$:

$$ \alpha(x) = \frac{D_F(x)^{-2}\, P(F|c(x))}{D_F(x)^{-2}\, P(F|c(x)) + D_B(x)^{-2}\, P(B|c(x))} $$

Composite

$J(x) = \alpha(x)\,c(x) + (1-\alpha(x))\,B_{new}(x)$, where $B_{new}$ is background.jpg resized to the video frame size (allowed — the aspect ratio of the background need not be preserved). The lecture's pure-foreground-color recovery matters most for wispy hair over a saturated old background; our band is narrow and the old corridor background is nearly neutral, so the direct blend introduces no visible halo. The alpha map itself is written to alpha_ID1_ID2.avi scaled to [0,255] uint8 (FAQ #5), replicated to 3 channels.

Key idea Histogram + Gaussian blur is KDE. The elegant low-rank story from the lecture becomes a one-liner when the color space is quantized to 256 bins per channel.

4   Tracking

Lecture — why filtering (Video_Processing.pdf, pages 28–30)

"In practice, we do not always have a high frame rate… and the object may move significantly between frames. In such cases, the initial guess can be far from the ground truth… To address this, we can make assumptions about the motion of the object — assumptions that will later be used by Kalman and Particle filters. For example, we might assume that the object moves along a straight line, with constant velocity, or with constant acceleration. Using one of these assumptions, we can predict the object's motion according to the chosen model and refine our initial guess."

Lecture — Kalman filter equations (Video_Processing.pdf, pages 30–34)
$$ \text{Project: } \hat{x}_{k+1}' = \Phi \hat{x}_k, \qquad P'_{k+1} = \Phi P_k \Phi^T + Q $$
$$ \text{Update: } K_{k+1} = P'_{k+1} H^T \big(H P'_{k+1} H^T + R\big)^{-1} $$
$$ \hat{x}_{k+1} = \hat{x}_{k+1}' + K_{k+1}\big(z_{k+1} - H \hat{x}_{k+1}'\big), \qquad P_{k+1} = (I - K_{k+1} H) P'_{k+1} $$
What our code does — Code/tracking.py

Automatic selection — no manual initialization

The task says to select the person in the matted video automatically. The matted video has a property we built ourselves: wherever there is no person, a matted frame equals the (resized) background image exactly (up to codec noise). So the detector is one line of algebra per frame: $\max_c |J_t(x) - B_{new}(x)| > 30$ → morphology → largest connected component → bounding box. That box is the measurement.

Kalman filter over the box

State $x = [\text{row}_c, \text{col}_c, h, w, v_{row}, v_{col}]^T$: constant-velocity dynamics for the box center (the lecture's second motion assumption — a walking person barely accelerates over 1/30 s) and a random walk for the box size. Measurement $z = [\text{row}_c, \text{col}_c, h, w]$. Each frame runs Project (predict); when a detection exists it runs Update, fusing prediction and measurement with the Kalman gain $K$; when the detection is missing the filter simply keeps predicting — the rectangle coasts through the gap instead of vanishing. The filter smooths the jitter of the raw per-frame boxes (measurement noise $R$ is set larger than process noise $Q$ for the size components, so the box breathes slowly instead of flickering with the leg swing).

Outputs

The smoothed box is drawn as a green rectangle on every matted frame → OUTPUT_ID1_ID2.avi, and written per frame to tracking.json as {"1": [ROW, COL, HEIGHT, WIDTH], "2": …} — top-left corner, integer values, one entry per frame of INPUT.avi, exactly the format of the project PDF.

Rules of thumb we relied on
  • Stabilize to a reference frame, not to a smoothed path, when the scene is static — it turns the hard background-subtraction problem into an easy one.
  • Never blur during stabilization — the matting band needs the sharp boundary colors (the project PDF warns about exactly this).
  • Robust statistics beat online updates offline — median/MAD give the dominant background Gaussian per pixel with zero foreground contamination.
  • Shadows live in luminance — test chroma separately (Lab) and re-label "darker, same chroma" pixels as background.
  • Trimap band ρ ≈ 5–15 px (lecture) — we use 10: wide enough for soft edges, narrow enough for the Euclidean≈geodesic approximation to hold.
  • A Kalman filter is cheap insurance — it smooths box jitter and coasts through missed detections with the constant-velocity assumption.
