The border that wouldn't hold still

Stabilization warps every frame with its own fresh homography, so the black padding around the frame isn't a fixed crop — it grows and shrinks continuously. Two attempts at masking it out, one real regression, and the fix that survived both. All numbers and frames below are from the actual project video and the actual shipped functions.

1The setup

Stabilization re-fits a homography to frame 0 every single frame — no fixed crop, no composed transform. That's good for drift (errors can't accumulate), but it means the warp's black border is a different shape on every frame.

raw frame
→
warpPerspective(frame, transform)
→
stabilized frame + black border
Background subtraction ran at half resolution and needed some way to tell "this pixel is real scene" from "this pixel is warp padding" — that boundary is what this whole page is about.

2Attempt 1 — one static guess for the whole video

The original approach: look at each pixel's dominant trained color across the whole clip. If it's basically black, assume that pixel is border and exclude it. Computed once, used unchanged on every frame.

# old code — one mask, built once, reused for all 205 frames
valid = (bg_mean[..., 0] > 15).astype(np.uint8)
valid = cv2.erode(valid, np.ones((7, 7), np.uint8))
# ... same `valid` array reused in the loop for every frame

Problem: a pixel near the edge might be border on 60% of frames and real content on 40% — its dominant color could go either way, and either way, one fixed answer is wrong for the other case.

bug — confirmed

On the frames with the largest camera drift, the true border reaches further than the static guess ever accounted for. Padding pixels inside the "trusted" zone get run through classification like normal scene pixels — and since they're solid black, they don't match anything, so they're flagged as foreground.

3Attempt 2 — exact geometry, no more guessing

The fix: stop guessing. Stabilization already computes a fresh transform every frame to build the warp — return it, and re-warp a blank white canvas with that exact same transform. Whatever comes back is the true valid region for that frame, pixel-accurate, no threshold involved.

stabilize_video() # now returns transforms[i] = the 3x3 homography used for frame i

# in background_subtraction, per frame:
valid_small = cv2.warpPerspective(
    white_canvas, T_small, (w_small, h_small),
    flags=cv2.INTER_NEAREST, borderValue=0)

This is geometrically exact and has zero video-specific tuning — no hardcoded drift amount, no brightness threshold. It fixed the seam completely.

new bug — confirmed

It also broke something else. A patch of ceiling near the top-left of frame 0 turned into a solid rectangle of false "person."

Why geometry alone isn't enough

Measured directly: that ceiling patch is warp border in 71% of all 205 frames — on the majority of frames, there's simply no real data there. The background model's own training is dominated by "black," because that's almost always what's there. Frame 0 is the exception (identity transform, no drift yet) — the geometry mask correctly says "this frame has real content here," but the model was never given a fair chance to learn that content as background, so classification alone doesn't trust it. 4The fix — require both signals to agree

Neither signal is wrong, exactly — each is blind to something the other one sees. So the shipped fix doesn't pick one, it ANDs them: a pixel only survives if this frame's exact geometry says it's inside the warp, and that pixel's own trained history isn't chronically black.

static_valid = (bg_mean[..., 0] > 15).astype(np.uint8)
static_valid = cv2.erode(static_valid, np.ones((7, 7), np.uint8))

for frame, small, T_full in zip(frames, small_frames, transforms):
    valid = static_valid
    if T_full is not None:
        T_small = S @ T_full @ S_inv
        valid_small = cv2.warpPerspective(valid_canvas, T_small, (w_small, h_small),
                                          flags=cv2.INTER_NEAREST, borderValue=0)
        geo_valid = cv2.erode((valid_small > 127).astype(np.uint8), np.ones((3,3), np.uint8))
        valid = valid & geo_valid  # must clear BOTH

End to end, across the whole clip: mask-area frame-to-frame jitter dropped from a std-dev of 2.46 (static-only) to 0.47 (hybrid) — the mask stopped randomly ballooning and shrinking frame to frame. Frames with a false-positive strip in the left 200 columns dropped from 83 out of 205 to 9.

5Why this doesn't just overfit this one video

Every number above is a measurement, not a dial that got tuned to this clip:

  • The geometry signal has no tunable parameter at all. It's the literal warp transform stabilization already computed for that frame — same math regardless of how much the camera shakes, how bright the room is, or how long the clip runs.
  • The color-history threshold (15, eroded 7px) already existed — reused as-is, not widened or narrowed to fit this failure.
  • The scale factor between full-res and half-res is measured from the actual resize (w_small / w_full), not assumed to be exactly 0.5 — so it doesn't quietly break on a video with odd width or height.

A video with a shakier camera just produces a bigger, faster-changing border — the geometry signal tracks it exactly either way, because it isn't measuring "how big is the border," it's re-deriving it from the same transform that built it.
